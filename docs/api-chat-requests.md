# API: чат с AI-buddy и заявки

Все запросы с `Authorization: Bearer <token>`. Ошибки: `{ "error": { "code", "message" } }`. Чат доступен только стажеру (наставник и руководитель получают 403). Схемы ответов во фронте: `frontend/src/schemas/assistant.ts`. Данные синтетические и не являются регламентами Авито.

| Метод | Путь | Что делает |
|---|---|---|
| POST | /api/chat/messages | вопрос помощнику, ответ – новые сообщения |
| GET | /api/chat/messages | последние 50 сообщений текущего диалога (восстановить чат) |
| POST | /api/chat/reset | «Новый диалог»: текущий диалог уходит в историю, неподтвержденные карточки отменяются |
| GET | /api/chat/dialogs | история диалогов, новые сверху (до 50) |
| GET | /api/chat/dialogs/{id}/messages | сообщения диалога для чтения, чужой – 404 |
| POST | /api/chat/actions/{actionId}/confirm | подтвердить действие: заявка уходит в систему заявок |
| POST | /api/chat/actions/{actionId}/cancel | отказаться от действия |
| GET | /api/requests | мои заявки, новые сверху |
| GET | /api/me/contacts | наставник и руководитель пользователя, отделы компании |

## POST /api/chat/messages

```json
{ "text": "Запроси доступ к GitLab", "action": null, "taskId": null }
```

- `text` – 1–2000 символов.
- `action` – действие задачи «Моего пути» (`task.action`), если стажер нажал «Сделать с AI-buddy». Тогда помощник не угадывает намерение, а сразу готовит нужное.
- `taskId` – эта задача: когда заявка выполнится, пункт пути закроется сам. Без `taskId` backend сам найдет незавершенную задачу с заявкой на этот сервис.

Ответ 200 – `{ "messages": ChatMessage[] }`:

```json
{ "messages": [
  { "id": "…", "role": "assistant", "kind": "text", "mood": "calm",
    "text": "GitLab согласует Олег, владелец проекта, обычно до 24 ч.",
    "source": { "title": "Доступы и сервисы → Как запросить доступ к сервису", "articleId": "c200…0004" },
    "confirm": null, "result": null },
  { "id": "…", "role": "assistant", "kind": "confirm", "mood": "mentor", "text": "Создать заявку на доступ?",
    "source": null, "result": null,
    "confirm": { "actionId": "f115…", "title": "Создать заявку на доступ?", "state": "pending", "fields": [
      { "label": "Ресурс", "value": "GitLab" },
      { "label": "Проект", "value": "backend / auth-service" },
      { "label": "Уровень прав", "value": "редактирование (Developer)" },
      { "label": "Обоснование", "value": "Нужен для задачи «Получить доступ к GitLab»" },
      { "label": "Согласует", "value": "Олег, владелец проекта" } ] } }
] }
```

Что умеет помощник:

| Вопрос | Ответ |
|---|---|
| «что такое код-ревью», «как проходят 1:1» | `text` из справочника со ссылкой на статью (`source`). Отвечает, только если в статье есть хотя бы половина слов вопроса |
| «запроси доступ к GitLab», «нужен тестовый стенд» | пояснение и карточка `confirm` |
| «дай доступ к логам продакшена» | `error`, `mood: sad`: доступ запрещен роли, причина из политики доступа |
| «хочу Maintainer» | `error` с предложением разрешенного уровня (Developer) |
| доступ уже выдан или заявка на согласовании | `text`, дубль не создается |
| «отгул в пятницу», «отгул 20.11 за свой счет» | пояснение и `confirm` с датой |
| «какой статус моих заявок», «что с заявкой №1038» | `text` со списком |
| «передай наставнику …» | `text`: вопрос ушел наставнику (или руководителю, если наставника нет) |
| ответа нет | `text` с предложением передать вопрос наставнику |

## Подтверждение и отмена

`POST /api/chat/actions/{actionId}/confirm` → `{ "messages": [ { "kind": "result", "result": { "requestId", "number": "1045", "title": "Доступ к GitLab", "status": "waiting" } } ] }`.

- Сервис без согласования (вики, трекер задач, трекер прогресса) выдается сразу: `status: "done"`, пункт пути закрыт.
- Остальное уходит согласующему: `waiting`, задача пути – «на согласовании» с пометкой «Заявка №1045 на согласовании: Олег, владелец проекта».
- 404 – действие уже выполнено, отменено или чужое. 503 `service_unavailable` – система заявок не ответила, черновик остается, можно повторить.

`POST /api/chat/actions/{actionId}/cancel` → сообщение «Хорошо, заявку не создаю».

## Решение согласующего

Backend каждые `REQUEST_SYNC_INTERVAL` (5 с) забирает решения из системы заявок. Когда решение есть:

- заявка → `done` (доступ выдан), `approved` (отгул согласован) или `rejected` с причиной;
- задача пути → выполнена, а при отказе снова «в работе» с причиной;
- стажеру приходит уведомление и сообщение помощника в чат («Готово: доступ к GitLab выдан»).

## GET /api/requests

```json
[{ "id": "…", "number": "1045", "kind": "access", "title": "Доступ к GitLab", "status": "waiting",
   "createdAt": "2026-11-11T18:27:00+03:00", "via": "buddy",
   "fields": [{ "label": "Ресурс", "value": "GitLab" }, { "label": "Проект", "value": "backend / auth-service" },
              { "label": "Уровень прав", "value": "редактирование (Developer)" }, { "label": "Обоснование", "value": "…" },
              { "label": "Согласует", "value": "Олег, владелец проекта" }],
   "history": [{ "title": "Создана AI-buddy", "at": "11 нояб, 18:27", "state": "done" },
               { "title": "Ждет решения: Олег, владелец проекта", "at": "обычно до 24 ч", "state": "now" }],
   "rejectReason": null }]
```

Черновики и отмененные заявки сюда не попадают. Если согласование идет дольше срока сервиса, в последнем шаге истории – «дольше обычного, AI-buddy напомнит».

## Кто согласует

| Сервис | Согласующий |
|---|---|
| Трекер задач, вики, трекер прогресса | выдается автоматически |
| GitLab | владелец проекта (backend/auth-service – Олег, frontend/web-app – Нина) |
| Тестовый стенд, логи продакшена | DevOps (Кирилл) |
| Отгул | руководитель команды |

Если согласующий не найден, заявка уходит руководителю команды.

## Система заявок (mock-services)

Отдельный контейнер, REST, контракт – `GET http://localhost:8090/openapi.yaml`. Решение согласующего приходит через `MOCK_DECISION_DELAY` (45 с). Принять решение вручную:

```
POST http://localhost:8090/v1/tickets/ACC-8001/decision
{ "approve": false, "reason": "Сначала пройди инструктаж по безопасности" }
```

Номер `ACC-…` хранится в `requests.external_ref`. Для внедрения достаточно новой реализации интерфейса `integrations.Corporate` поверх настоящей системы заявок.

## Модель

`LLM_PROVIDER=mock` (по умолчанию) работает без ключа: намерение по ключевым словам, ответ из найденного фрагмента справочника. `LLM_PROVIDER=openai_compat` подключает любой OpenAI-совместимый API (Yandex AI Studio, Cloud.ru, Avito A-Vibe через Ollama; подробно – `docs/llm-setup.md`) с function calling: модель выбирает инструмент, backend проверяет права и выполняет. Если модель не ответила за `LLM_TIMEOUT`, ответ собирается офлайн, чат не падает. Каждый вызов модели и инструмента пишется в `agent_tool_calls` (время, статус) для метрик.

Модель видит не только текущий вопрос, но и последние 8 сообщений переписки и карточку, которая ждет «Подтвердить». Поэтому на «что делать сейчас?» помощник отвечает по состоянию чата: подтвердить карточку выше, ждать решения по заявке (с номером и согласующим) или открыть «Мой путь». Пока карточка не подтверждена, вторую такую же он не создает. Без ключа (mock) подсказку собирает backend по тем же данным.

Пояснение над карточкой заявки формулирует модель, а факты (кто согласует, сроки) берутся из базы. Если в тексте модели нет хотя бы одного числа или имени из исходного текста или он слишком длинный, показывается текст backend: модель не может подменить согласующего или срок.


## Заявки в отделы

Кроме доступов и отгулов помощник оформляет заявки в отделы: отдел оборудования (ноутбук, монитор, гарнитура, клавиатура и мышь, пропуск), ИТ-поддержка (VPN, почта, сброс пароля, второй фактор), HR-поддержка (отпуск, справка с места работы, документы для вуза, изменение личных данных), бухгалтерия (справка 2-НДФЛ, вопрос по выплате). Каталог – таблицы `departments`, `catalog_items`, `catalog_aliases` (миграция 013).

Заявка в отдел имеет `kind: "other"`. Поля карточки: «Что нужно», «Комментарий», «Исполняет» (после выполнения – «Выполнил»). После «Подтвердить» заявка уходит в mock-services с `kind: "other"` (номер `SD-…`), отдел решает автоматически через `MOCK_DECISION_DELAY`, наставник стажера получает уведомление со ссылкой `/interns/{id}`. О наставнике получает уведомление и при заявке на отгул.

## Сохранение переписки

Каждое сообщение стажера и помощника пишется в `messages` сразу, вместе с источником и ссылкой на заявку. `GET /api/chat/messages` возвращает последние 50 сообщений текущего диалога в том же формате, что и ответ на `POST`: карточки подтверждения приходят с актуальным состоянием (`pending`, `confirmed`, `cancelled`), карточки результата – с текущим статусом заявки. Сюда же попадают сообщения о решении согласующего или отдела, которые backend пишет сам.

Фронт держит переписку в кеше запросов (`['chat', 'history']`): при переходе на другую страницу чат не теряется, после перезагрузки загружается из backend. Пока в чате есть заявка на согласовании, переписка обновляется раз в 15 секунд, чтобы ответ пришел без перезагрузки.

«Новый диалог» (`POST /api/chat/reset`) ничего не удаляет: текущий диалог закрывается и попадает в историю, открывается новый (таблица `chat_dialogs`, миграция 016). Пустой диалог не закрывается. Неподтвержденные карточки закрытого диалога отменяются, поэтому в истории они приходят с `state: "cancelled"`. Модель видит только сообщения открытого диалога. Ответ – `{ "messages": [] }`.

## История диалогов

`GET /api/chat/dialogs` → `[{ "id", "title", "preview", "kind", "updatedAt", "current" }]`. Сначала открытый диалог (`current: true`), потом прошлые по времени последнего сообщения. Прошлые диалоги без сообщений не показываются.

- `title` – первая реплика стажера, до 60 символов; у пустого открытого диалога – «Новый диалог».
- `kind` и `preview` – итог: была заявка (`request`, «Заявка №1042 создана», «… одобрена», «… выполнена», «… отклонена»), вопрос передан наставнику (`handoff`, «Передано наставнику»), иначе `answer` («Ответ из справочника» или «Разговор с AI-buddy»).
- Заголовок и итог не хранятся, а считаются по сообщениям диалога, поэтому всегда совпадают с перепиской (например, заявка одобрена позже – итог обновится сам).

`GET /api/chat/dialogs/{id}/messages` → `{ "messages": ChatMessage[] }`, тот же формат, что `GET /api/chat/messages`. Сообщение попадает в открытый диалог триггером базы, поэтому решение по заявке из старого диалога приходит в текущий.
